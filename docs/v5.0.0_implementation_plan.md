# Unified nanoTesla (nT) Architecture

## Background
Currently, the firmware processes magnetic data in **raw integer counts** directly from the RM3100. Because the hardware gain scales dynamically with the Cycle Count setting, a raw count of `1000` at 200cc represents a vastly different magnetic field than `1000` at 800cc.
To cope with this, the firmware currently intercepts Cycle Count changes and manually multiplies the Hard-Iron calibration offsets and live Tare offsets by the relative scale factor. This causes accumulation errors and suffers from the RM3100's non-linear Zero-Field Offsets (ZFO), causing the UI's `nT` value to drift when cycling through hardware gains.

## SemVer Bumping (Breaking Changes)
Because this transition completely changes the units of the calibration matrix from raw counts to `nT`, old `calibration.json` files will no longer work with the new firmware. Following standard Semantic Versioning rules for breaking changes, we will apply **Major** version bumps:
- **Firmware (`user_config.h`):** Bump to **`v5.0.0`**
- **Python (`calibrate_wand.py`):** Bump to **`v2.0.0`**

## The Goal
Shift the entire mathematical architecture into physical space (`nT`). The firmware will convert the raw I2C bytes into `nT` *before* applying any calibration math. The Python calibration script will also convert logs into `nT` *before* fitting the ellipsoids.
This completely decouples the calibration from the hardware gain. Cycle counts can be changed dynamically without ever touching the calibration matrix or Tare offsets.

> [!WARNING] 
> **Breaking Change:** This update changes the unit of the `tip_hard` and `ref_hard` arrays in `calibration.json` from raw counts to `nT`. **You will need to perform a fresh Fig-8 calibration** using the updated Python script after flashing this firmware, or your wand's baseline will be wildly off. (Note: You can re-run the updated Python script against your existing 400cc characterization logs, as the script will default to 400cc if the column is missing).

## Proposed Changes

### 1. Python Calibration Script
#### [MODIFY] `scripts/calibrate_wand.py`
- Update the data loader to extract the `cc` (Cycle Count) column from the CSV logs. (Fallback to 400 if using old logs).
- Convert `refX_raw`, `tipX_raw`, etc. into `nT` arrays frame-by-frame: `nT = (raw * 1000.0) / (0.38 * cc)`.
- The Kabsch algorithm and Ellipsoid fit will now run entirely in `nT` space.
- The resulting `calibration.json` will natively store the hard-iron centers in `nT`.
- **Version Bump:** Bump the script's `__version__` to `v2.0.0`. Bump the output `matrix_version` in the JSON from `2.0` to `3.0`.

### 2. Firmware Sensor Fusion
#### [MODIFY] `src/sensor_fusion/SensorFusion.h` & `.cpp`
- Add an inline helper: `float raw_to_nT(int32_t raw, uint16_t cc)`.
- Change `calibration_offset` and `auto_tare` variables from `int32_t` (raw counts) to `float` (nT).
- In `processUpdate()`:
  1. Immediately convert `tip_raw` and `ref_raw` integers into `float` nT vectors using the active `cycle_count`.
  2. Apply the Hard-Iron and Soft-Iron matrices directly to these `nT` vectors.
  3. Calculate `gradX, gradY, gradZ` directly in `nT`.
- Remove the `scaleTare(float scale)` function completely. (Scaling is no longer mathematically required).

### 3. Main Firmware Loop
#### [MODIFY] `Magnetic_Field_Scanner.ino`
- In the `task_sensor_read` loop, completely delete the block of code that intercepts CC changes to multiply `cal_config.tip_hard` and calls `sensorFusion.scaleTare()`.
- The firmware will simply update the hardware I2C registers and move on.

### 4. Fix Sensor Lockup (The Lapping Issue)
#### [MODIFY] `Magnetic_Field_Scanner.ino`
- **The True Root Cause:** The user brilliantly identified the physical root cause of the lockup loop. When the SD Card performs a 20ms block to write to flash memory, the RM3100 completes a cycle and pulls `DRDY` HIGH. It then completes a *second* cycle, and `DRDY` stays permanently HIGH. Because the ESP32 is waiting for a `RISING` edge interrupt, the ISR never fires again, the EventGroup times out, and the watchdog trips! The watchdog then calls `initRM3100()`, but does *not* do a dummy read to clear the `DRDY` pin. The pin stays HIGH forever, bricking the wand until a power cycle!
- **The Fix:** Right before calling `xEventGroupWaitBits`, the firmware will manually poll `digitalRead()` on both `DRDY` pins. If either pin is already `HIGH` (meaning we were lapped), it will manually set the EventGroup bit via software, bypassing the need for a RISING edge interrupt!
- **I2C Speed Boost:** As the user suggested, we will increase the `i2c_master_init` frequency to `200KHz`. We will **not** use `400KHz` because the 60-inch CAT6 cable creates significant capacitance. Even with the parallel 4.7K pull-up resistors, `400KHz` is too fast for the RC time constant of a 5-foot cable and will cause data corruption. `200KHz` is the perfect sweet spot for safety and speed margin.
- **Watchdog Dummy Read:** The watchdog timeout handler will be updated to perform a dummy read of `REG_RESULTS` *before* attempting re-initialization, ensuring the `DRDY` pin is forcefully dragged back to `LOW`.

### 5. User Interface
#### [MODIFY] `src/lvgl_port/lvgl_port.c`
- **Main VuMeter Label:** Update the huge number in the center to print the physical `nT` value with 0 decimal places (`%.0f`).
- **Secondary Label:** Replace the small `nT` label with `RAW: <magnitude>`. This provides a direct window into the hardware state, which is incredibly useful for diagnosing saturation, checking slew rates, or confirming that the chosen cycle count is providing the physical sensitivity you desire.
- **Color Thresholds:** The arbitrary raw count thresholds (2000, 5000) will be replaced with absolute physical thresholds based on typical magnetic anomaly signatures (e.g. Iron Pipe at 2 feet):
  - **Green (Background):** `0 - 150 nT`
  - **Yellow (Anomaly):** `150 - 500 nT`
  - **Red (Strong/Close Target):** `> 500 nT`
- **Arc Range:** Rescale the arc limit to `5000 nT` (down from 10000 raw counts).

### 6. IMU Temperature Logging
#### [MODIFY] `src/imu_bsp/imu_bsp.h` & `.c`
- Update `imu_read()` to read 14 bytes starting from register `0x33` (TEMP_L) instead of 12 bytes from `0x35`.
- Parse the QMI8658 internal die temperature (16-bit integer, 1 LSB/degC).
#### [MODIFY] `src/data_logger/data_logger.cpp`
- Append the `imu_temp` column to the SD card CSV log. Because the RM3100 magnetometer is notoriously sensitive to thermal drift (its RC oscillators change frequency with heat), logging the IMU temperature allows the Python script to potentially correlate and compensate for thermal drift during long surveying sessions!

### 7. SD Card Data Logging Impact
#### [MODIFY] `src/data_logger/data_logger.cpp`
The raw counts will continue to be logged exactly as they come off the sensor, ensuring data integrity for future Python calibrations. However, several downstream calculated columns in the CSV will automatically change units from raw counts to `nT`.
Because `nT` is a calculated floating point value, we will log these specific float columns with **2 decimal places** (`%.2f`). At our highest sensitivity (3200cc), the physical hardware resolution is `0.82 nT` per count. Logging to 2 decimal places perfectly preserves the absolute mathematical resolution of the silicon without unnecessarily inflating the CSV file size with meaningless floating-point dust.
- **Unchanged (Raw Counts):** `tipX_raw`, `tipY_raw`, `tipZ_raw`, `refX_raw`, `refY_raw`, `refZ_raw`.
- **Changed to nT (%.2f):** `tipX_cal`, `tipY_cal`, `tipZ_cal`, `refX_cal`, `refY_cal`, `refZ_cal`.
- **Changed to nT (%.2f):** `calOffsetX`, `calOffsetY`, `calOffsetZ` (Tare offsets).
- **Changed to nT (%.2f):** `gradX`, `gradY`, `gradZ`, `mag`.
*(Note: Because `mag` will now mathematically be identical to the `nT` column, we will leave the duplicate `nT` column in the CSV for backwards compatibility with any existing user Python scripts).*

### 8. Downstream Python Script Updates
#### [MODIFY] `scripts/characterize_system.py`, `analyze_scan.py`, `analyze_log.py`
All auxiliary Python reporting and graphing scripts will be updated to accommodate the new native `nT` columns. Specifically:
- `characterize_system.py` will have its manual `nT` math stripped out to prevent applying the conversion scale factor twice, restoring correct Allan Variance and Noise Floor analysis.
- Plotting scripts will have their Y-axis labels updated from "Counts" to "nanoTesla (nT)".
- Outlier filtering thresholds (e.g., `max_mag`) will be re-tuned for physical `nT` limits.
